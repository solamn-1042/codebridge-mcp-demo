# CodeBridge：仓库接手与改动复核的 Agent 工具插件

## 为什么开发

目标场景是开发者让 Coding Agent 接手一个本地仓库：解释项目结构、定位一段实现、阅读相关代码，核对修改前后的差异，并运行固定检查。

原版 CodeBridge 只有概览、改动统计和 pytest 检查。统计信息能告诉 Agent 哪些文件变化，却无法提供代码证据。Agent 必须切换到其他工具才能搜索、读取和看具体 diff，仓库路径、读取大小与失败信息也分散在不同调用中。

因此将插件定位为“仓库上下文与改动验证入口”：提供统一的相对路径与结果格式，把代码定位、证据读取和改动复核连起来。核心需求是更清楚地回答“在哪里实现、具体改了什么、检查是否通过”，而不是堆叠任意 Shell 操作。

## 需求如何转成设计

| 场景需求 | 实现选择 | 产生的作用 |
|---|---|---|
| 第一次接手仓库，不知道项目结构 | repo_overview 返回 README、清单与分支 | 先建立项目范围，再定位代码 |
| 需要找到具体实现 | search_code 返回路径、行号和短片段 | 让后续读取有明确目标 |
| 大量代码不能一次全部塞给模型 | read_file 按行读取，并给出 next_start_line | 按需补充上下文，明确截断位置 |
| staged/unstaged 容易混淆 | git_diff 明确模式，返回文件级 patch | 根据具体增删行解释修改 |
| 模型拼命令容易出错，失败信息不好解释 | 固定 test 名称，统一退出码、输出和错误码 | 不向模型开放任意命令字符串 |
| 服务异常不应要求重启整个运行时 | 保留状态与重连控制入口 | 在同一 Cordis 运行时恢复连接 |
| 缺少可复查的效果数据 | SQLite 元数据与真实 stdio benchmark | 区分调用耗时、策略拒绝及后续可用性 |

## 如何想到这个方向

设计从实际的仓库接手流程出发，将任务拆成“建立背景—定位实现—读取证据—复核差异—验证结果”。原版只覆盖第一步、改动统计和最后一步，中间最需要代码证据的环节缺失。因此补齐 search_code、read_file 和 git_diff，再统一它们的路径与输出边界。

新增工具描述明确提示下一步可用的工具，但调度仍由 DSH 的模型与 Agent Loop 决定；项目没有自研规划器或训练算法。

## 技术栈选择

- Python：复用已有语言基础，使用 pathlib、subprocess 和 sqlite3 完成文件、Git 与观测功能；MCP SDK 负责协议与工具 Schema。
- TypeScript 与 Cordis：符合 DSH 原生插件接口。TypeScript 只承担服务生命周期管理，业务工具留在 Python。
- MCP 与 stdio：将业务工具和 Agent 运行时分开，服务作为本地子进程运行，不增加 HTTP 端口和独立鉴权配置。
- 官方 DSH MCP Client：复用已有连接、发现与工具注册逻辑，避免重复编写协议客户端。
- Git：直接读取仓库已有工作区与暂存区状态，避免另建变更数据库；调用使用参数列表，并关闭外部 diff/textconv。
- SQLite：本地可持久化，不需要部署 MySQL；仅保存调用元数据，方便统计和核查。
- pytest 与 Node 原生测试：验证真实仓库操作、MCP 会话和 Cordis 生命周期。测试服务于开发质量，项目定位仍是 Agent 应用工具扩展。

## 与现有同类工具的取舍

官方 [Filesystem MCP Server](https://github.com/modelcontextprotocol/servers/tree/main/src/filesystem) 提供广泛的文件读写、搜索及目录访问控制；官方 [Git MCP Server](https://github.com/modelcontextprotocol/servers/tree/main/src/git) 提供状态、diff 以及提交等 Git 操作。它们适合通用文件和 Git 操作。CodeBridge 的差异是将一个固定本地仓库的代码上下文、差异复核、固定检查和观测组织在同一套接口里。

| 维度 | CodeBridge 的选择 | 适合的需求 |
|---|---|---|
| 操作范围 | 相对路径、文件级 diff、无文件编辑/Git 写操作工具 | 读取证据与复核改动 |
| 上下文组织 | 路径、行号、短片段、按行续读 | 控制单次代码上下文体积 |
| 执行入口 | 固定 pytest 检查，不接受命令字符串 | 在可信 Python 仓库验证结果 |
| DSH 操作 | 状态、启停、手动重连 | 排查本地工具服务故障 |
| 观测 | 元数据落 SQLite，提供统计工具 | 复现调用与异常后可用性 |

这些是面向特定场景的取舍，没有对同类项目做性能优劣实测。通用文件管理、动态目录 Roots、Git 写操作或跨语言构建需求更广时，现有通用服务器更合适。

官方 [DSH MCP Client](https://github.com/deepseek-ai/deepseek-harness/tree/master/packages/mcp/mcp-client) 已提供工具发现、命名空间和自动重连等能力。CodeBridge 自己的工作是业务工具、路径/输出策略、元数据记录，以及显式启停和手动重连的 Cordis 管理层；不能把官方底层能力写成自研成果。

## 异常处理为什么这样设计

业务级错误返回结构化错误码，让 Agent 能识别路径拒绝、文件缺失、读取预算和命令超时。SDK 层缺参或类型错误由 MCP SDK 拒绝。两种错误都通过真实 MCP 测试验证后续合法调用仍可执行。

服务启动失败时，管理插件保留控制工具并暴露错误，修复环境后可重连。服务进程崩溃时，手动重连释放旧 MCP Client 并重新发现工具。验证覆盖同一 Cordis 运行时，不等于完整模型对话自动恢复率。

检查命令不会被自动重跑，因为测试代码可能有副作用，不能默认假定重试是幂等的。当前配置关闭官方客户端自动重连，让手动重连的行为与验证范围更清楚。

## 指标如何解释

tool_benchmark.json 来自本机、临时小型 Git/Python 仓库、真实 stdio MCP 调用。它测量工具执行与通信，不测量模型推理、真实用户满意度或生产任务完成率。正常调用与故意制造的拒绝请求分别统计，不把策略拒绝当作业务故障。

P95 耗时包含 IPC，样本数量较少且仓库很小；可用于本地回归参照，不能推广为大型仓库的性能。run_project_check 在该评测中仅执行一次，其单次耗时不宜当作稳定 P95 指标。

路径控制是应用层限制：已知凭证文件排除不等于完整秘密检测，pytest 也不是沙箱。项目没有宣称生产级权限隔离、容器部署、RAG、自动代码修改或完整 Agent Loop 自研能力。
